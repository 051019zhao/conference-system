# 数据库性能优化报告(openGauss 实测)

> 本报告所有执行计划均为在本系统 openGauss 5.0.0 容器上真实执行的 `EXPLAIN ANALYZE` 输出摘录,
> 测试数据为 5 万行模拟论文(通过 `generate_series` 批量生成后清理)。
> 生成方式:数据库性能基准脚本见 `backend` 外 `D:\bench*.sql`,可在任意环境复现。

## 一、优化项总览

| 优化项 | 数据库能力 | 验证结果 |
|---|---|---|
| 审计日志 RANGE 分区 | openGauss 分区表(按月) | **分区裁剪实证:Selected Partitions: 1** |
| 论文全文检索 | tsvector + GIN 倒排索引 + 触发器维护 | 高选择性查询走 **Bitmap Index Scan on idx_paper_search** |
| 评审匹配下沉函数 | plpgsql 函数 + CTE + 返回表 | `SELECT * FROM fn_match_experts(id)` 原子完成匹配/回避/去重 |
| 专题录用率排名 | CTE + 窗口函数 RANK() OVER | 仪表盘"专题录用率排名"卡片 |
| 高选择性索引扫描 | B-tree(含 Index Only Scan) | **Index Only Scan using idx_paper_status** |

## 二、openGauss 分区表(审计日志按月 RANGE 分区)

`paper_status_log` 与 `operation_log` 是只增不改的日志表,采用按月 RANGE 分区:
查询自动做**分区裁剪**(只扫命中月份的分区),历史分区可整体卸载(TRUNCATE/DETACH)归档。

**分区裁剪实证**(2026 年 10 月的日志查询只选中 1 个分区):

```
 Partition Iterator  (cost=0.00..3.16 rows=1 width=1028) (actual time=0.022..0.027 rows=20 loops=1)
   ->  Partitioned Seq Scan on operation_log  (cost=0.00..3.16 rows=1 width=1028) (actual time=0.019..0.023 rows=20 loops=1)
         Selected Partitions:  1        ← 只访问了 1 个分区,其余分区零 IO
```

设计要点:分区键 `created_at` 必须包含在主键中,故主键为复合主键 `(id, created_at)`——这是分区表的标准约束。

## 三、全文检索(tsvector + GIN + 触发器维护)

论文标题/关键词常含英文,采用 PG 式全文检索:
- `paper.search_vector TSVECTOR` 列由**触发器 `trg_paper_search`** 在 INSERT/UPDATE title、keywords 时自动维护;
- 其上建 **GIN 倒排索引** `idx_paper_search`;
- 查询:`search_vector @@ plainto_tsquery('simple', 关键词)`,与 `ILIKE '%kw%'`(中文兜底)OR 组合。

**5 万行数据高选择性查询实测**(命中 50 行):

```
 Aggregate  (cost=502.21..502.22 rows=1 width=0) (actual time=0.555..0.555 rows=1 loops=1)
   ->  Bitmap Heap Scan on paper  (cost=296.43..502.07 rows=56 width=0) (actual time=0.506..0.546 rows=50 loops=1)
         ->  Bitmap Index Scan on idx_paper_search  (cost=0.00..296.42 rows=56 width=0)
                                                            ← GIN 索引定位,无需全表扫描
```

## 四、B-tree 索引与 Index Only Scan

高选择性状态查询在 5 万行下触发 **Index Only Scan**——整个查询不回表读堆数据:

```
 ->  Index Only Scan using idx_paper_status on paper  (cost=0.00..12.18 rows=29 width=0)
                                                    (actual time=0.244..0.854 rows=50 loops=1)
```

## 五、优化器的"反直觉"选择(理解索引何时无用)

同样在 5 万行上,当查询命中约 47% 的行(低选择性)时,优化器**主动放弃索引改用顺序扫描**:

```
 ->  Seq Scan on paper  (cost=0.00..3019.03 rows=23669 width=0) (actual time=0.020..10.310 rows=23751 loops=1)
```

这不是性能问题,而是优化器的正确决策:命中近半张表时,逐行走索引回表的随机 IO 代价高于顺序读全表。
**理解"索引不是万能的"与理解"索引如何加速"同等重要**——这是本系统在性能实验中得到的真实结论。

## 六、评审匹配的数据库函数

自动分配的匹配/回避/去重规则全部下沉到 plpgsql 函数 `fn_match_experts(paper_id)`
(CTE 拆词 + 相关子查询打分 + RETURNS TABLE 返回候选),应用层仅 `LIMIT 2` 取前二。
SQL 层原子完成意味着:任何调用方(未来的脚本、其他服务)得到的匹配口径完全一致。

## 七、结论

1. 分区表解决审计日志的增长与归档问题(分区裁剪实测生效);
2. GIN 全文索引解决论文检索问题(高选择性查询实测走索引);
3. 索引收益与查询选择性强相关——低选择性场景应信任优化器选择顺序扫描;
4. 业务规则适度下沉数据库函数,可获得跨调用方的原子性与一致性。
