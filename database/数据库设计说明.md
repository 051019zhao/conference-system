# 会议管理系统 数据库设计说明

> 数据库:openGauss 5.x(Docker 部署,兼容 PostgreSQL 协议)
> 建表脚本:`backend/src/main/resources/schema.sql`(后端启动时自动执行,亦可手工执行)

## 一、E-R 模型(概念设计)

系统核心实体及关系如下:

```
用户 sys_user ──1:1── 专家档案 expert_profile ──1:N── 主旨报告 keynote_report
   │
   │ (角色:ADMIN 管理员 / EXPERT 专家 / AUTHOR 作者,单表 + 角色字段)
   │
   ├──1:N──(作为投稿人 submitter)── 论文 paper ──N:1── 专题 topic
   │                                        │
   │                                        ├──1:N── 论文作者 paper_author
   │                                        └──1:N── 评审 review ──N:1──(专家)
   │
会议信息 conference_info(单行)   日程 schedule_item   通知 notification   资料 material
```

设计要点:

1. **三种角色共用一张用户表**,用 `role` 字段(CHECK 约束)区分。角色间共性(账号、密码、邮箱)远大于差异,拆成三表会造成大量重复和三处登录逻辑;专家的独有属性(职称、单位、研究方向)放在 `expert_profile` 表中,与 `sys_user` 一对一关联。
2. **论文与作者是多对多关系**,通过 `paper_author` 关联表实现,`sort_no` 字段维护作者排序(第一作者为 1),`is_corresponding` 标记通讯作者——满足"多作者、可编辑排序"的需求。
3. **评审 review 是论文与专家之间的关联实体**,带自身属性(总评、修改意见、结论、是否推荐期刊)。`UNIQUE(paper_id, expert_id)` 在数据库层面保证"同一专家不重复评审同一篇论文"。
4. **论文摘要等大文本用 TEXT**,枚举类状态用 `VARCHAR + CHECK 约束`而非应用层枚举,保证非法状态无法写入数据库。

## 二、论文评审状态机

```
                 管理员初审通过            专家提交评审意见后管理员终审
 SUBMITTED ────────────────> REVIEWING ────────────────> ACCEPTED(录用)
 (已投递)                    (外审中)  │                      │
      │                                └──> REJECTED(退稿)   │ 提交终稿
      └──────> REJECTED(初审退稿)                             v
                                                     FINAL_SUBMITTED(终稿已提交)
```

- 状态流转全部由**后端 Service 层校验 + UPDATE**完成,非法流转(如未录用就提交终稿)在业务层直接拒绝;
- 每次状态变化由**触发器 `trg_paper_status`** 自动写入 `paper_status_log`,实现数据库层面的操作审计。

## 三、逻辑设计(范式分析)

所有表均满足 **第三范式(3NF)**:

- 非主属性完全函数依赖主键,无部分依赖(如作者信息不冗余存进 paper,而是独立成表);
- 无传递依赖(如论文不存"专题名称"而存 `topic_id`,名称从 topic 表关联获取)。
- **例外与权衡**:`review` 表保存评审结果快照而不是只存意见,因为评审结论属于该关联实体自身的属性,不属于冗余。

## 四、数据库特色功能(课程知识点覆盖)

| 知识点 | 应用位置 | 说明 |
|---|---|---|
| 视图 | `v_paper_stats` | 按专题 × 状态统计论文数,管理后台仪表盘直接查询该视图 |
| 触发器 | `trg_paper_status` | 论文状态变更自动写审计日志,不依赖应用代码 |
| CHECK 约束 | `sys_user.role`、`paper.status`、`review.result` 等 | 数据库层拒绝非法枚举值 |
| 唯一约束 | `sys_user.username/email`、`review(paper_id, expert_id)`、`topic.name` | 防止重复注册、重复分配评审 |
| 外键级联 | `paper_author`、`review` 对 paper `ON DELETE CASCADE` | 删论文时自动清理从属数据 |
| 索引 | 外键列、`paper.status`、`schedule_item.day` 等 | 加速高频过滤查询;可用 `EXPLAIN` 验证 |
| 事务 | 投稿(论文+多作者)、分配评审(删旧待审+插新)、终审 | 多表写操作保证原子性 |

## 五点五、论文文件存储设计(大小分流 + 版本账本)

论文 PDF 和附属资料(压缩包)是大文件,头像是小图片,两者采用**不同的存储策略**,这是本系统最重要的存储设计决策:

| 对象 | 大小 | 存储方式 | 理由 |
|---|---|---|---|
| 论文主稿/终稿/附属资料 | 数 MB ~ 20MB | **磁盘存内容,`paper_file` 表存元数据** | 大对象入库会使事务日志(WAL)膨胀、备份变慢、缓冲池被挤占;元数据入库保留可查询性与约束 |
| 用户头像 | 几十 KB ~ 2MB | **BYTEA 直接入库**(`user_avatar` 独立表) | 小而低频,入库免磁盘管理;垂直拆分避免主表膨胀;展示数据库大对象能力 |

`paper_file` 版本账本设计:

```
file_type: MAIN(投稿主稿) / FINAL(终稿) / SUPPLEMENT(附属资料 zip/rar/7z/pdf/图片)
version_no + is_current: 同一类型可有多个版本——重传主稿时旧版本保留(is_current=false)
                        供追溯,新版生效;UNIQUE(paper_id, file_type, version_no) 数据库层保证版本号不冲突
uploaded_by: 记录每个附件的上传者(审计)
paper 表的 file_path / final_file_path 作为"当前主稿"的冗余指针,加速高频查询
```

该设计同时满足了:多附件(附属资料任意多个)、论文版本(初稿多版+终稿)、以及附件与论文的级联删除(ON DELETE CASCADE)。

## 六、安全性设计

- 密码使用 **BCrypt 加盐哈希**存储,数据库不存明文;
- 登录态使用 JWT,敏感接口(投稿/评审/后台管理)在拦截器中校验角色权限,且**每请求实时查库校验账号状态**;
- 评审专家只能看到分配给自己的论文与自己的评审,作者只能在论文有结论后查看**彻底匿名**(无姓名无ID)的评审意见;
- 上传文件做**内容级魔数校验**(PDF 的 `%PDF-`、zip 的 `PK`、7z/rar 各自文件头),仅凭扩展名判断会被伪造;
- `verify_code` 设置 5 分钟过期且一次性使用(`used` 标记),防止验证码重放。
